# Print Designer HTML/CSS bridge plan

## Objective

Let users finish a layout in Print Designer, then avoid duplicate work by exporting a Jinja-compatible HTML + CSS bundle that can be copied into a standard `Print Format` (`print_format_type = "Jinja"`).

A secondary goal is a limited import path back into Print Designer, but only under controlled rules because Print Designer stores `header`, `body`, and `footer` as separate structured layout trees rather than a single free-form HTML document.

## Current codebase findings

### Design View entry and editor

- Route entry: `print_designer/print_designer/page/print_designer/print_designer.js`
- Vue app: `print_designer/public/js/print_designer/`

- Save pipeline: `print_designer/public/js/print_designer/store/ElementStore.js`
- Top header UI: `print_designer/public/js/print_designer/components/layout/AppHeader.vue`

### What Print Designer saves today

`ElementStore.saveElements()` persists:

- `print_designer_header`
- `print_designer_body`
- `print_designer_footer`
- `print_designer_print_format`
- `print_designer_settings`
- `css`

Important: it does **not** persist a complete ready-to-paste `html` field for standard Jinja Print Formats.

### Existing backend rendering path

Print Designer already renders through Jinja templates/macros:

- `print_designer/pdf.py`

- `print_designer/print_designer/page/print_designer/jinja/old_print_format.html`

This means Print Designer already has a server-side path that turns saved designer JSON into final rendered HTML/Jinja.

### Existing import/export features

Current export/import already exists here:

- `print_designer/api/print_format_export_import.py`
- `print_designer/public/js/print_format/print_format.js`
- `print_designer/public/js/print_format/print_format_conversion_dialog.js`

But current features are for:

- Print Designer JSON backup/restore
- wrapping Print Format JSON into a Designer-export package

They are **not** a bridge for pure HTML + CSS.

## Feasibility summary

### Export: Print Designer -> Jinja HTML + CSS

**Feasible and low-to-medium risk.**

Reason:

- designer layout data already exists
- CSS already exists in saved `Print Format.css`
- backend Jinja templates already know how to render the layout
- `userProvidedJinja` is already part of `print_designer_settings`

### Import: HTML + CSS -> Print Designer

**High risk if arbitrary HTML is allowed.**

Reason:

- Print Designer is a structured object model, not a DOM editor
- plain HTML/CSS does not reliably preserve semantic objects like:
  - static vs dynamic text
  - header vs body vs footer
  - table metadata
  - barcode/image metadata
  - page variants (`firstPage`, `oddPage`, `evenPage`, `lastPage`)
- arbitrary pasted HTML loses the structure needed to rebuild draggable designer elements

## Import constraint required for safety

If import is implemented, the safest workflow is **template-first import**, not free-form paste.

Recommended workflow:

1. user downloads a bridge template generated by Print Designer
2. template already contains required section markers and placeholder structure
3. user pastes HTML into the correct section only:
   - Header
   - Content
   - Footer
4. user pastes CSS into the CSS section
5. importer validates the template before any save occurs

Recommended required markers:

```html
<!-- PD:HEADER:START -->
...
<!-- PD:HEADER:END -->

<!-- PD:CONTENT:START -->
...
<!-- PD:CONTENT:END -->

<!-- PD:FOOTER:START -->
...
<!-- PD:FOOTER:END -->

<!-- PD:CSS:START -->
...
<!-- PD:CSS:END -->
```

Without this template structure, import should refuse to run or stay in preview/validation mode only.

## Product recommendation

Treat this as a **bridge**, not a generic HTML parser.

Supported direction priorities:

1. **Export from Print Designer to Jinja HTML + CSS**
2. **Create Jinja copy automatically** from a Print Designer format
3. **Import only bridge-compatible HTML/CSS** with explicit markers and optional embedded metadata
4. Do **not** promise arbitrary HTML/CSS round-trip fidelity

## Proposed phases

## Phase 1 - Export only MVP

Goal: let the user export a Print Designer format into two copyable outputs:

- HTML
- CSS

### UI

Add action in Design View header, likely in:

- `print_designer/public/js/print_designer/components/layout/AppHeader.vue`

Possible labels:

- `Export Jinja HTML`
- `Export CSS`
- `Export HTML + CSS`

### Backend

Add a new API in:

- `print_designer/api/print_format_export_import.py`

Suggested method:

- `export_print_format_as_jinja_bundle(print_format_name)`

### Export payload

Return structured payload:

```json
{
  "print_format_name": "Receipt",
  "html": "...",
  "css": "...",
  "schema_version": "1.3.0",
  "source": "print_designer"
}
```

### Rendering strategy

Reuse the existing backend Jinja rendering path instead of inventing a second renderer.

Expected sources:

- `print_designer_print_format`
- `print_designer_settings`
- `print_designer_header`
- `print_designer_body`
- `print_designer_footer`
- `Print Format.css`
- `userProvidedJinja`
- Jinja style macros (`styles.html` / `styles_old.html`)

### Important implementation note

Saved `Print Format.css` alone is not enough. Export must also include wrapper/page CSS logic from the Jinja macro layer.

## Phase 2 - Create Jinja copy automatically

Goal: eliminate manual copy/paste.

Instead of only showing HTML/CSS, add an action like:

- `Create Jinja Copy`

This should:

- create a new `Print Format`
- set `print_format_type = "Jinja"`
- fill `html`
- fill `css`
- keep original Print Designer format unchanged

Good UI candidates:

- Design View header action
- Print Format form menu in `print_designer/public/js/print_format/print_format.js`

## Phase 3 - Bridge package for safe round-trip

Goal: support reliable re-import of exported HTML/CSS.

Exporter should optionally emit a bridge package with:

- `html`
- `css`
- explicit header/content/footer comment markers
- embedded metadata block containing source schema and layout JSON

Possible metadata pattern:

```html
<!-- PD:METADATA:START -->
{...json...}
<!-- PD:METADATA:END -->
```

This gives the importer a trustworthy source of truth rather than trying to infer everything from free-form DOM/CSS.

## Phase 4 - Controlled import into Print Designer

Goal: import bridge-compatible HTML/CSS back into designer storage.

### Rules

- Require a generated import template as the default import path
- Require explicit section markers for header/content/footer/CSS
- Prefer embedded metadata if present
- Reject arbitrary unmarked HTML
- Show validation result before save
- Let users fill the template part-by-part instead of trying to infer sections automatically

### Backend target fields to rebuild

- `print_designer_header`
- `print_designer_body`
- `print_designer_footer`
- `print_designer_print_format`
- `print_designer_settings`

### Realistic scope

Supported first:

- text blocks
- absolute positioning
- simple images
- simple rectangles

Later / harder:

- dynamic fields
- tables
- barcode
- advanced page variants
- complex nested flow containers

## Key risks

1. Header/footer page variants:
   - `firstPage`
   - `oddPage`
   - `evenPage`
   - `lastPage`
2. table semantics and pagination
3. barcode and image metadata
4. `userProvidedJinja` integration
5. old schema compatibility
6. print differences between browser, wkhtmltopdf, and chrome generators
7. impossible fidelity if arbitrary HTML/CSS is accepted

## Recommended implementation order

1. Backend export API for HTML + CSS
2. Design View UI button to preview/copy bundle
3. Optional `Create Jinja Copy` action
4. Bridge metadata format
5. Controlled import validator
6. Controlled import save flow

## Decision recorded

For import, use a **template-first bridge workflow**.

The import package should require user-supplied content inside predefined comment sections for:

- Header
- Content
- Footer
- CSS

because Print Designer stores layout as separate structured sections and arbitrary HTML cannot be safely split or reconstructed without explicit structure.
